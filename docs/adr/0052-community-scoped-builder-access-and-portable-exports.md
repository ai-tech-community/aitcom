# Community-scoped builder access and portable exports

[Open community platform redesign](../superpowers/specs/2026-11-28-open-community-platform-redesign-design.md), items 13 and 14. Builds on [ADR-0015](0015-community-surfaces-are-human-authored.md), [ADR-0017](0017-agent-communication-boundary-and-manifest.md), [ADR-0025](0025-real-time-delivery-is-asymmetric.md) and [ADR-0050](0050-private-communities-follow-the-join-policy.md).

Communities need stable interfaces for tenant integrations, and owners need a copy of the tenant's data they can use elsewhere. The platform already issues agent keys, serves tools over MCP, and delivers signed agent webhooks. Those interfaces have an agent and owner boundary. This ADR defines the additional tenant boundary for builder access and portability.

## Decision

### Identity and community scope

- Serve the public builder contract at `/api/v1/communities/{communitySlug}/…`. V1 starts with `GET /spaces`, `GET /posts` with an optional `spaceId` filter, `GET /events` and `POST /post-drafts` relative to that tenant root. Public developer docs explain scopes, setup, example requests, rate limits, events and migration policy. Use an OpenAPI document as the REST contract. All tenant plans, including free communities, get the same initial capabilities and quotas.
- A Better Auth session and current tenant owner role are required to mint, rotate and revoke credentials and to manage subscriptions. The v1 REST operations use `Authorization: Bearer <token>`. Browser cookies do not confer REST builder access. Keys are opaque random secrets, shown once, with a distinct prefix, SHA-256 digest at rest, a visible label, expiration and revocation. Reuse the generation and validation pattern in `src/server/agent/api-key.ts`. Rotate by issuing a successor, with an explicitly bounded overlap, and revoke immediately on request. Store issuer and last-use information. Invalidate keys the issuer can no longer administer, with an owner-transfer UI that identifies credentials to reissue.
- Resolve the slug to one tenant and bind the key to that tenant's immutable ID. Every object lookup constrains community and object together. Evaluate capability, current role or membership, then the exact resource policy. Use `src/server/communities/content-access.ts`, `content-visibility.ts` in that directory and the data model's own restrictions, including paid access, room membership and course/publication visibility. Start with `spaces:read`, `posts:read`, `events:read` and member-agent draft scopes. The initial published read API supplies space names, published posts and event summaries, with no roster emails or attendee answers. A different tenant or a resource hidden from the principal yields the same 404 as a missing record.
- Keep the existing Streamable HTTP endpoint at `src/app/api/mcp/route.ts` with its server and tool registration in `src/app/api/mcp/server.ts` and catalog in `src/server/mcp/catalog.ts`. Keep the existing bearer validator, current manifest check in `src/server/agent/api-key.ts` and per-tool authorization in `src/server/api/trpc.ts`. A claimed agent calls the new tools with its existing agent key and a selected community. For the new tools it additionally needs a grant issued by the tenant owner, linked to that key with the agent owner's consent. The agent owner must remain an eligible member. The effective permissions are the intersection of the key's scopes, manifest acceptance, tenant grant and the agent owner's current ACL. The pre-existing MCP tools and registration mode keep their contracts. Invalid presented credentials get an auth failure. An unclaimed or suspended agent gets no new tenant access.
- A tenant REST integration may read permitted data. The first write capability, creating a draft for human review, requires a linked agent identity and uses the same agent grants and existing draft guards as MCP. Reuse `src/app/api/mcp/feed-tools.ts`, `src/server/api/routers/agent-feed.ts` and `src/server/api/routers/agent-own-drafts.ts`. Approval re-runs the human write policy. Token management, member administration, export and direct publishing are outside the starter scopes.

### Protocol

- **Rate limits.** Start at 60 requests per minute per token or delegated agent key and 300 per minute per tenant, with a separate small IP budget for failed authentication. Count a valid logical REST request or MCP tool invocation once at its own application boundary. Keep the legacy agent limiter for existing tools, reusing the check-on-invocation pattern from `src/server/api/trpc.ts`. Use a shared atomic Redis budget for the new tenant interface, following the shared store precedent in `src/server/collectors/context/site-rate-limit.ts`. Return 429 and `Retry-After` on exhaustion and a retryable 503 when the shared limiter cannot make a decision. Publish quota values and tune them from observed usage.
- **Idempotency.** Require `Idempotency-Key` on REST writes and an equivalent operation ID on any mutating MCP tool that exposes the new contract. Store a unique key by tenant, principal, operation and request key, together with a canonical input hash, state and replay result, for 24 hours after completion. Claim and persist the effect and result with the same unit of work, or resume by a stored effect ID after interruption. Reauthorize before replay. Same payload returns the original result, concurrent in-flight duplicates get a retryable conflict, and different payload under the same key gets `IDEMPOTENCY_CONFLICT`. Export and import use their own durable request IDs.
- **Pagination.** List endpoints use a default page size of 25 and maximum of 100, an opaque authenticated cursor bound to the community, filter and sort, and a stable tuple such as `(createdAt, id)`. Return `{ "data": [], "nextCursor": null }` at the end. Reject malformed or mismatched cursors with 400. Recheck authorization on every page. Live pagination may reflect new writes or removals. Export declares a distinct snapshot boundary.
- **Errors.** REST failures use `{ "error": { "code": "NOT_FOUND", "message": "Resource not found", "requestId": "…" } }`. Codes and status mappings are versioned. Return 400 for invalid input, 401 for missing or invalid credentials, 403 for missing permission on a visible resource, 404 for hidden or absent resources, 409 for conflicts, and 429/503 for retryable capacity failures. Responses carry a correlation ID without stack traces, secrets or private object details. MCP keeps its transport envelope and supplies the equivalent machine-readable code for new tool failures.
- **Versioning.** Pin REST to `/api/v1`, webhook envelopes to `schemaVersion: 1`, and archives to their own `formatVersion: 1`. Add backward-compatible fields within a version. Publish a new version, migration guide and deprecation window before breaking a contract. MCP adds versioned tool contracts through the existing catalog and server identity in `src/server/mcp/identity.ts`. Keep registered tool names and schemas working during a migration.

### Community webhooks

An owner chooses an HTTPS endpoint and topics in Settings → Developers. V1 includes `post.published`, `event.published`, `event.updated` and `member.joined`. Events carry the stable event ID, topic, tenant, schema version, occurrence time and minimum useful entity references. The membership topic requires an explicit membership-event grant and sends a tenant-local membership reference. Omit contact fields, DMs and attendee answers from all topics.

Record deliveries through an outbox written with the domain transaction when the write seam supports it. For a write through an existing independent store, derive the same stable event ID from a durable committed source record and reconcile missing outbox entries with a worker. Give each subscription and event one logical delivery ID. Recheck subscription state and data scope before queued delivery or retry. Claim deliveries with a lease, bound retries over 24 hours with backoff, send at least once and allow explicit owner replay. Keep a 30-day history of attempts, timestamps, status codes and failure reasons. Receivers deduplicate by event ID and should handle out-of-order delivery.

Sign the exact request body with HMAC-SHA256 over `timestamp + "." + rawBody` using a per-subscription secret. Send `X-AIT-Timestamp` and `X-AIT-Signature: v1=<hex>`. Document constant-time verification and a five-minute timestamp window. Reuse the signing precedent in `src/server/agent/deliver-event.ts` and the outbox pattern in `src/server/payments/outbox.ts`. Encrypt secrets at rest using application-managed key material, support a short bounded rotation overlap, and redact secrets, headers and response bodies from history. Use the public address policy and pinned transport in `src/server/net/safe-fetch.ts` for every attempt, including connection and redirect checks. Use a short timeout and bounded response. This scheduling is separate from ADR-0025's reactive agent wake, which keeps its own owner approval and delivery semantics.

### Ownership and archive contents

The current owner starts jobs, polls status and requests a download from the community's Portability settings. Recheck ownership at each boundary, including when claiming the job and issuing the download. Store the ZIP as a private object, retain it for seven days by default and issue short-lived download URLs (at most five minutes). Ownership transfer invalidates job access for the prior owner. Stop issuing links immediately and revoke the active artifact route or let an already issued object URL expire within its five-minute bound. Keep the request and access audit metadata separate from the archive. Reuse the job state and claim pattern in `src/server/collectors/runs.ts`, the worker entry pattern in `src/app/api/cron/collector-worker/route.ts` and the storage adapter in `src/server/media/object-storage.ts`. Materialize the approved rows and media references from a consistent snapshot before streaming the archive. Record any media that becomes unavailable after the snapshot by source ID.

The versioned ZIP contains the following:

| File or section | Content |
| --- | --- |
| `manifest.json` | Format version, source tenant, snapshot time, entity counts and schema versions, checksums, media inventory, omission reasons and warnings. The snapshot covers committed records at the declared source boundary. |
| `members.csv` and `members.jsonl` | Tenant membership IDs, portable profile and attribution fields, role, status and join date. Include membership contact email only where it is already available to that owner as tenant roster data. Record a destination identity mapping hint and preserve attribution even when a source member never joins the destination. |
| `data/*.jsonl` | Portable community settings and theme ID, rules, links, topics, groups, spaces, discussion posts and comments, forum threads/replies, room content where owners already have lawful read access, events and portable RSVP state, hackathon records, course hierarchy and permitted enrollment/progress, and community-owned content from launchpad, gallery, ideas, offers, reels, rituals, blog, news configuration and magazine. Include cross-record source IDs, original timestamps, access/publication state, and owned relationship/count data. |
| `media/` | Bytes and checksums of transferable community-owned uploads. Reference external or provider-bound content by safe identifier or URL and report missing media or dependencies by source ID. A shared Hub or other-tenant reference is a reference, with no copy of its target contents. |

The per-entity export registry includes a field allowlist, access rule and import support verdict for each current tenant collection or app relation. A supported record that cannot be exported gets an explicit error or manifest warning. Omit platform credentials, password hashes, sessions, subscriber contact data and individual reading traces, private DMs and owner–agent conversations, active invite codes, secrets, payment credentials and live subscriptions, organizer-only attendee contact and registration answers, private matching responses and lesson notes, unrelated Hub activity, and other communities' data. Subscription and payment state can be summarized where permitted for migration, without replaying a charge or silently enabling access. Platform account deletion and a member's personal data rights stay separate from community export.

An import validates version, checksums, limits, relationships and media before it writes. Preview the counts, omissions, ID mappings and any work required from the owner. Apply to a fresh, unlisted, invite-only target owned by the requester. Create new IDs, remap references, keep source attribution, and associate existing Hub accounts only after verified identity and consent. Unmatched people are imported as attributed historical contributors with an optional invitation path. The target stays restricted during restore. Content gated in the source remains gated and the owner explicitly publishes or opens access on the target. Use the staged import map and archive digest to resume safely without duplicates. Suppress notifications, XP, webhooks, checkout and external publishing during restore. A failed import leaves an inaccessible staged set that can be resumed or discarded. Report provider-bound media or settings, unmatched members and every omission. Release verifies the round trip across supported entities, including private media relationships and access states.

Reuse tenant role names for historical membership records, but leave imported administrative roles inactive until the target owner grants them through existing member controls. Preserve source visibility when mapping content links and keep staged objects private until the destination applies the import. Resolve source file references against the archive's checked manifest.

## Rejected alternatives

- **Expose tRPC or Payload collections as the integration API.** These are internal contracts and do not supply a stable tenant-facing permission, error or versioning boundary.
- **Grant a community-wide admin token every privilege or make an agent impersonate its owner.** A leak would confer permissions far beyond an integration and sidestep human approval and current membership.
- **Reuse the agent-wake cursor as the community delivery log.** The existing wake mechanism addresses an agent and its owner. Community subscriptions need durable per-event attempts, replay and different payload rules.
- **Send the export as emailed CSVs or a raw database dump.** Separate sheets lose relationships and media. A dump mixes tenant, platform and secret state. Use a versioned archive with an explicit field contract.
- **Restore in place or reenroll everyone automatically.** A fresh target makes rollback and validation tractable, and account association can preserve member consent.

## Consequences

- Items 13 and 14 each own one additive migration, reserved in the redesign spec. Both retain existing auth and persistence seams.
- Every new integration resource needs tests for same-tenant and cross-tenant IDs, hidden data, role changes and revocation. Every new export adapter needs a manifest and round-trip fixture.
- Artifact and delivery retention impose storage and operations costs. Owners get visible expiration, failure, and retry states, while logs retain bounded metadata.
