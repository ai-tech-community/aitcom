# Community statistics: available data and trustworthy metrics

Date: 2026-10-30. Scope: source-code research for an owner/admin dashboard. No live database was queried or written, so the presence and historical completeness of production rows remain unverified. Sources below are repository files; line numbers refer to this checkout.

## Findings that shape the dashboard

1. **Extend Insights rather than create a second analytics destination.** `/communities/[slug]/insights` already composes a health pulse, activation funnel, at-risk list, newcomer list, and unanswered-contribution list. Its current pulse compares trailing 14 days with the preceding 14 days. Sources: [dashboard](../../src/components/communities/insights/insights-dashboard.tsx#L8), [router](../../src/server/api/routers/insights.ts#L69).
2. **Current membership and logged participation are different measurements.** Membership is one mutable row per community/user, with active/pending/invited/banned statuses. Events are timestamped actor/action records with optional community attribution. Use membership for present member counts and events for recorded activity trends. Sources: [membership schema](../../src/server/db/schema.ts#L4038), [event schema](../../src/server/db/schema.ts#L1837).
3. **Do not call all distinct event actors “active members.”** The existing health loader does not filter `actorType` or join active membership; it counts distinct actor IDs for selected actions. The event schema permits member, agent, and system activity, and its actor ID is not a foreign key to membership. Label historical distinct humans as “contributors” after filtering `actorType = 'member'`; use a current active-membership join for a current-member participation rate. Sources: [health loader](../../src/server/api/routers/insights.ts#L77), [summarizer](../../src/server/communities/insights.ts#L66), [writer](../../src/server/agent/activity.ts#L95), [event schema](../../src/server/db/schema.ts#L1846).
4. **Recorded joins and voluntary leaves do not support an exact member-balance or churn chart.** Leaving deletes the member row and logs `community.left`; bans and removals instead log separate actions, currently without `communityId`. Agent-assisted joins can use the agent as actor and identify the human in `metadata.onBehalfOf`. Count join events without a human-actor filter, and label them “recorded joins,” not distinct new people. Sources: [leave](../../src/server/api/routers/communities.ts#L881), [ban/remove](../../src/server/api/routers/communities.ts#L1246), [agent join](../../src/server/api/routers/agent-communities.ts#L317).
5. **`joinedAt` is not a universal activation timestamp.** It defaults when a membership row is inserted; activating an existing invitation/pending row updates status without resetting it. A “members joined in period” query over membership describes surviving rows created in that period, not all completed joins. Sources: [schema](../../src/server/db/schema.ts#L4064), [activation writer](../../src/server/communities/activate-membership.ts#L46).

## Existing contribution definition and instrumentation

The implemented contribution set contains feed posts/comments, forum threads/replies, idea submit/vote, launchpad publish/vote/update/comment, event register/intent/create/submit, and challenge enrollment/submission/completion. It excludes likes, views, administrative actions, Hub article actions, room chat, and course enrollment/completion. Keep this set explicit and visible in metric help; a contribution count is not an all-purpose engagement or visit count. Source: [canonical implementation](../../src/server/communities/insights.ts#L17). The domain document describes the human-participation intent and explicitly excludes passive signals and commissioned work: [CONTEXT](../../CONTEXT.md#L535).

Representative current emitters set community ID for feed posts/comments, forum replies/ideas, events, launchpad activity, and challenge enrollment/submission. Sources: [feed](../../src/server/api/routers/feed.ts#L502), [comment](../../src/server/api/routers/feed.ts#L1144), [forum reply](../../src/server/api/routers/forum.ts#L573), [idea](../../src/server/api/routers/forum.ts#L264), [event](../../src/server/api/routers/events.ts#L332), [launchpad](../../src/server/api/routers/launchpad.ts#L312), [challenge](../../src/server/api/routers/challenges.ts#L266). This establishes available instrumentation, not complete historical coverage.

The historical backfill covers only community join/leave/join-request events whose community target can be copied. It does not backfill past content events. Do not assert coverage since community creation or reconstruct cumulative membership history from event sums. Source: [migration](../../src/migrations/20260530_backfill_membership_community_id.ts#L4).

**Attribution is not proof of manual activity.** Scheduled ritual threads are logged with `actorType = member` and the ritual owner's user ID. The final metric labels should therefore say “Member contributors” and “Member contributions,” with help text explaining recorded attribution, instead of claiming all member-type events are manually human-authored. Source: [ritual writer](../../src/server/communities/post-ritual-thread.ts#L56).

Membership activation commits before its activity event is logged, so a failed post-commit log can leave membership and event totals different. This is another reason to treat the stock and logged-flow metrics separately. Source: [activation sequence](../../src/server/communities/activate-membership.ts#L102).

Actor-type separation is available, but **member-attributed does not guarantee a manual human gesture**: scheduled ritual threads log `actorType: 'member'` using their author's ID. Agent forum threads use the agent ID/type and `metadata.onBehalfOf` for the human author. Prefer the UI labels “Member contributions” and “Agent contributions,” with attribution explained, rather than promising a perfect human-versus-automation split. Sources: [ritual emitter](../../src/server/communities/post-ritual-thread.ts#L56), [thread emitter](../../src/server/communities/create-forum-thread.ts#L68). Classroom `course.enroll` does carry community ID but remains outside the current heartbeat taxonomy: [emitter](../../src/server/api/routers/classrooms.ts#L1235).

## Access control and existing operational metrics

The middleware authenticates the user, resolves a non-deleted community by slug, loads that user's membership, and exposes a role only for active membership. It does **not** itself require a managerial role. Each analytics endpoint must enforce owner/admin or the chosen manager policy before reading aggregates. Source: [middleware](../../src/server/api/trpc.ts#L250).

Current Insights navigation, layout, router, and activation router permit owner/admin/moderator. A new owner/admin-only statistical endpoint can be stricter without changing the existing moderator outreach tools; ensure the new UI is hidden to moderators as well. Sources: [navigation](../../src/components/communities/community-nav.tsx#L77), [layout](../../src/app/[locale]/communities/[slug]/insights/layout.tsx#L21), [insights gate](../../src/server/api/routers/insights.ts#L38), [activation gate](../../src/server/api/routers/activation.ts#L67).

At-risk means an active-status member with contributions during the prior 45-day lookback but none in the trailing 14 days; the list is capped at 50, so its displayed length is not an uncapped at-risk population total. Unactivated means active-status members whose membership timestamp is 3–30 days old and who have no logged contribution ever. Both input loaders exclude commissioned metadata. Sources: [selectors](../../src/server/communities/insights.ts#L118), [loaders](../../src/server/communities/insights-queries.ts#L42).

The existing activation funnel uses active members with membership timestamps in the past 30 days, their first recorded contribution, a timely response, and configurable profile completion. Default response window is seven days. Reciprocity metadata is forward-only; do not present this as mature cohort retention, and do not silently make the cohort follow an unrelated 7/30/90-day statistics filter. Sources: [cohort loader](../../src/server/api/routers/activation.ts#L37), [contribution/response loading](../../src/server/api/routers/activation.ts#L123), [activation logic](../../src/server/communities/activation.ts#L28), [domain caveat](../../CONTEXT.md#L545).

## Recommended first statistical surface

Build an aggregate overview above the operational Insights panels, using a bounded 7/30/90-day selector (30-day default), adjacent equal-length comparison windows, and explicit timezone/date boundaries.

| Metric | Definition | Interpretation |
|---|---|---|
| Current members | Count active membership rows | Point-in-time stock; no unsupported historical delta. |
| Human contributors | Distinct member-actor IDs with canonical contribution actions in the selected period | Historical participation; can include people who subsequently left. |
| Recorded contributions | Count member-actor canonical contribution events in the selected period | Activity volume, not content still published or total interactions. |
| Recorded joins | Count community.joined events in the selected period, including agent-assisted joins | Join events, potentially repeat joins, not guaranteed distinct new people. |
| Recorded leaves | Count community.left events in the selected period | Voluntary leaves recorded; excludes administrative removals/bans. |
| Current-member participation | Distinct current active membership user IDs with member-actor contribution events / current active member count | A current-member engagement snapshot, not historical retention. |
| Contribution trend | Daily counts of the same qualifying contribution events | Zero-filled buckets, selected timezone, no passive/read signals. |
| Contribution mix | Counts grouped into explicit canonical action categories | Labels such as discussions, ideas, events, projects, challenges. |
| Membership breakdown | Current rows by status, active rows by role | Supports links to member/request management; snapshot unaffected by date filter. |

For zero comparison baseline, show “New activity” when current > 0 and “No change” when both zero; never show `+∞` (current pulse does). For empty denominators, display no rate or 0% with the underlying zero cohort clearly stated. Source of current infinity behavior: [health UI](../../src/components/communities/insights/health-pulse.tsx#L6). These display rules and recommended metrics are design recommendations inferred from the source limitations above.

Defer exact cumulative membership curves, churn/retention rates, visits/sessions/unique visitors, revenue, and universal engagement scores. They require fuller lifecycle history, telemetry, or a separately agreed definition. Magazine readership, event attendance, and classroom statistics can follow as independently defined panels rather than being added into the contribution heartbeat silently.

## Implementation seams

- Add a pure statistics module beside `src/server/communities/insights.ts` for interval construction, zero-filled daily buckets, group mapping, comparison outputs, and DTOs. Inject a clock. Use explicit `[start, end)` bounds so future-dated rows never enter the current period.
- Add a read-only aggregate loader beside `insights-queries.ts`. Use SQL aggregates over the existing community/action/time index instead of fetching every historical event into the browser; scope every source to the resolved community ID.
- Add an owner/admin-gated query to the existing `insights` router. Return only aggregate numbers/series, not raw actor IDs, private content, emails, or message text.
- Add UI components beneath `src/components/communities/insights/` and preserve the existing operational panels and their fixed-window definitions. Reuse repository chart components/tokens and `next-intl` translations.
- Unit-test the changed pure statistics files and authorization-facing route files with mocked data only. Cover period boundaries, zero baselines, empty communities, actor types, agent-assisted join events, null community attribution, commissioned exclusions, and cross-community isolation. Run only touched/added test files plus the changed workspace's type-check; no integration tiers or database writes.

## Open decisions

1. Whether the new aggregate statistical view should be strictly owner/admin or retain existing moderator access. The requested audience supports owner/admin-only; preserving moderator operational tools avoids an unrelated permission regression.
2. Whether “contributors” is the clearer default KPI or whether the product wants a current-active-member participation KPI. The definitions above can coexist if labels distinguish them.
3. The dashboard timezone. UTC is deterministic and easy to label; viewer-local buckets need a validated timezone passed to the backend. Community-local time requires a community timezone field or another explicit source.

The [approved dashboard design](../superpowers/specs/2026-10-30-community-statistics-design.md) resolves these: owner/admin-only new aggregates while preserving moderator tools; member-attributed contributors rather than a participation-rate KPI; and complete UTC calendar-day periods with explicit dates. Greg confirmed growth and participation as the first priority and approved the design on 2026-10-30. The dashboard is implemented against these definitions; see the design document for verification and remaining data limitations.
