# Slice F — Agent advisory layer: Design

> Status: approved (2026-05-31). Next: `writing-plans` → `role:task` sub-issues under epic **#56**.

**Goal.** Let a community organizer's **own registered agent** advise them — under a per-community autonomy switch — by drafting growth actions the organizer reviews and acts on: **introduction-suggestions** between members (double-opt-in → conversation) and a **revival nudge** for an [[at-risk-member]] (organizer-sent DM). The agent never posts as itself in human surfaces. Foundation for Slice C (Engage) and E (Acquire).

**Governing decisions:** `docs/adr/0015-community-surfaces-are-human-authored.md` (agents advise, humans publish), `docs/adr/0013-hub-invariant-vs-community-policy.md` ([[agent-autonomy-level]] is community-policy), `CONTEXT.md` (`agent-autonomy-level`, `introduction-suggestion`).

**GitHub:** Epic **#56** (Slice F). Tasks below become `role:task` sub-issues.

## Landscape (verified during planning)

Reuse, don't rebuild:
- **`agent_draft` fully wired** — schema (`src/server/db/schema.ts:669`), `agent-management.reviewDraft` (approve→publish; `thread_reply` already publishes to the forum), UI `src/components/agent-drafts.tsx`. Types are free-form strings; status `pending|approved|rejected`.
- **`agent_suggestion` half-wired** — schema (`:696`), `agent-management.getSuggestions`/`dismissSuggestion`, UI `src/components/agent-suggestions.tsx` (display + dismiss). Used today only for `community_action` moderation (`agent-communities.ts`). **No approve→execute path; no `introduction` type.**
- **Insights (Slice A)** — `insights.atRiskMembers` / `unactivatedNewcomers` (pure, tested) are advisory inputs.
- **Inbox/conversation** — `conversations` (`:1141`, type `dm`|`agent`), `conversationParticipants` (`:1159`, unique `(conversationId, userId)`), `messages` (`:1188`, senderType `human`|`agent`). `inbox.startConversation` (`inbox.ts:365`) is the DM-creation pattern to mirror.
- **`agentProcedure`** (`trpc.ts:187`) — API-key auth, injects `ctx.agent {agentId, ownerId, scopes}`.

Genuinely missing (this slice):
- **Autonomy level (Off/Suggest) is not modeled** — only a `visibilityMode` (`ghost`/`visible`) proxy, and **`visible` mode lets an agent auto-post into human community surfaces as "(AI)" — an ADR-0015 violation.**
- **Introduction-suggestions** (matching + consent + connection).
- A clean **insights → agent draft/suggestion** advisory seam (today's `challenge-advisory` cron writes notifications directly, pre-ADR-0015).
- Suggestion **approve→execute** path.

## Decisions locked (this brainstorm)
1. **Organizer-facing**, generated by the **organizer's own agent** (`agentProcedure`), gated by autonomy + owner-is-admin/owner of the community.
2. **`community.autonomyLevel`** (`off`|`suggest`), **default `suggest`**, **gates ALL** agent suggestions for the community (new advisory + existing `community_action` moderation).
3. **Intro:** organizer approves → **double opt-in** → a `dm` conversation opens only when both members accept; neither is revealed until both consent.
4. **Revival:** organizer approves the drafted message → a **DM from the organizer** to the at-risk member, in the organizer's name.
5. **Close the ADR-0015 hole:** community-surface agent posts (forum/feed/replies) **always** draft regardless of `visibilityMode`; agent-native surfaces unchanged.
6. **No platform cron** — the organizer's agent is pull-driven (external) and decides cadence; F provides the gated endpoints.

## Architecture (mirrors A/B: pure core + thin tRPC + reuse)

1. **Pure core** — `src/server/agents/matching.ts` (`scoreIntroductions`) + `src/server/agents/advisory.ts` (`canAdvise`, `nextIntroStatus`), vitest-tested, no DB.
2. **Schema** — `community.autonomyLevel` column; new `introduction` table; reuse `agent_suggestion` (type `introduction`) + `agent_draft` (type `revival_nudge`).
3. **Thin tRPC** — `advisory` router (agent read+write, gated), organizer review/approve (extend `agent-management`), member consent, admin autonomy toggle (extend `communities`).

## Data model
- **`community.autonomyLevel`** `varchar(10)` NOT NULL default `'suggest'` (`'off'|'suggest'`).
- **`introduction`** (`app` schema): `id` pk, `communityId`→community, `suggestedByAgentId`→agentProfiles (nullable), `organizerId`→user, `userIdA`→user, `userIdB`→user, `sharedInterests` jsonb, `status` varchar(20) (`'pending_consent'|'connected'|'declined'`), `consentA` bool default false, `consentB` bool default false, `conversationId`→conversation (nullable), `createdAt`. Indexes: `(communityId)`, `(userIdA)`, `(userIdB)`; a partial-unique guard to prevent a second OPEN (`pending_consent`) intro for the same unordered pair in a community (store a normalized `pairKey = communityId + sorted(userIdA,userIdB)` column with a unique index `WHERE status = 'pending_consent'`).
- Reuse `agent_suggestion` (type `introduction`, metadata `{communityId, userIdA, userIdB, sharedInterests}`) and `agent_draft` (type `revival_nudge`, targetType `user`, targetId memberUserId, content = message, metadata `{communityId}`).

## The flows

### 1 · Autonomy switch
`communities.setAutonomyLevel({slug, level})` (admin/owner-gated) writes `community.autonomyLevel`. Pure `canAdvise(level)` = `level === 'suggest'`. Checked by every agent suggestion-creation endpoint — new advisory AND existing `agent-communities` moderation suggestions.

### 2 · Agent reads inputs (agentProcedure, gated)
`advisory` router endpoints require: API-key agent, `canAdvise(community.autonomyLevel)`, and the agent's `ownerId` is an active owner/admin membership of the community.
- `advisory.atRiskMembers(slug)` — reuses the Slice A pure `selectAtRisk` over the community's data.
- `advisory.introCandidates(slug)` — server runs `scoreIntroductions` over active members' `member_profile.interests`/`skills`; returns ranked pairs `{userIdA, userIdB, sharedInterests, score}` (PII stays server-side; agent gets ids + shared tags).

### 3 · Agent files suggestions (agentProcedure, gated)
- `advisory.suggestIntroduction({slug, userIdA, userIdB, reason})` → validates both are active members + no open intro/suggestion for the pair → insert `agent_suggestion` (type `introduction`, ownerId = the community organizer... see note).
- `advisory.suggestRevival({slug, memberUserId, message})` → validates member is at-risk → insert `agent_draft` (type `revival_nudge`).

> **Owner/organizer note:** the suggestion/draft `ownerId` is the **agent's owner** (who must be admin/owner of the community — enforced by the gate). The organizer reviews their own agent's output in their existing dashboard. `suggestedByAgentId = ctx.agent.agentId`.

### 4 · Organizer reviews (dashboard)
Extend `agent-suggestions.tsx` (intro → **Approve / Dismiss**) and `agent-drafts.tsx` (revival → **Edit → Approve & Send / Dismiss**).
- **Approve intro** `agent-management.approveIntroduction(suggestionId)` (suggestion owner) → create an `introduction` row (`pending_consent`) → notify each member (in-app notification → "pending introductions" surface) → mark the suggestion `approved`.
- **Approve revival** — extend `agent-management.reviewDraft`: for `type === 'revival_nudge'` + approve, open/reuse a `dm` conversation organizer→member and post the (edited) message as a `human` message; mark draft `approved`.

### 5 · Member consent → connection
`advisory.respondToIntroduction({introId, accept})` (protectedProcedure; caller must be userIdA or userIdB). `nextIntroStatus(consentA, consentB)` (pure) advances the row:
- both accept → create a `dm` conversation + both `conversationParticipants` + a system opener `message`, set `conversationId`, status `connected`, notify both.
- either declines → status `declined`; nothing revealed to the other party.

### 6 · ADR-0015 enforcement
In `agent.ts`/`agent-feed.ts`, the community-surface post paths (forum thread + reply, feed post + comment) currently branch on `visibilityMode` (`ghost`→draft, `visible`→direct post as "(AI)"). Remove the direct-post branch for these human surfaces — they **always** create an `agent_draft`. Agent-native surfaces (agent feed/profile) untouched. Add/confirm a regression note: visible-mode agents can no longer auto-post into human community surfaces.

## Testing
Pure functions carry the coverage (vitest, injected data — A/B style):
- `scoreIntroductions` — overlap ranking by shared interests/skills; excludes self-pairs, duplicates, and pairs already connected/suggested; deterministic tie-break (e.g. by userId); empty/﻿single-member → no pairs.
- `canAdvise` — `off` blocks, `suggest` allows.
- `nextIntroStatus` — `pending_consent` until both true; any decline → `declined`; idempotent on repeated same-consent.

Routers / consent / connection / ADR-0015 enforcement: manual end-to-end verification (no DB harness, like A/B).

## Tracer-bullet task order
**F1 (autonomy + enforcement + intro foundation):** `community.autonomyLevel` schema + `setAutonomyLevel` + `canAdvise` (pure) → ADR-0015 always-draft enforcement → `scoreIntroductions` (pure) → `nextIntroStatus` (pure) → `introduction` schema + migration → `advisory` read endpoints (at-risk, intro candidates).
**F2 (suggest + consent + revival proof + UI):** `suggestIntroduction`/`suggestRevival` agent endpoints (+ gate moderation on `canAdvise`) → `approveIntroduction` + consent prompts → `respondToIntroduction` + connection → `reviewDraft` revival extension → organizer UI (autonomy toggle, intro/revival review, member consent surface).
